# The agent simulation

A minimal implementation of the "Generative Agents" architecture from
[Park et al., 2023](https://arxiv.org/abs/2304.03442): characters that
remember what happens to them, periodically reflect on it, plan their day,
react to whoever they run into, and talk to each other. Hyperparameters
(recency decay, retrieval weights, reflection threshold) are taken directly
from the paper's [reference implementation](https://github.com/joonspk-research/generative_agents),
so behavior tracks the paper as closely as a small rewrite reasonably can.

The cast is a city's residents, generated by `history/` and grounded in its
real places (see `history/characters.py`). A run is started by a Simulation
node in the UI (`POST /api/agents/run`), runs on a background thread, and
streams every event to the frontend live. Afterward, a Treatment node can
turn that run into a film treatment with a shot list.

## An agent

An `Agent` (`agent.py`) is an identity plus a memory stream:

| Field | Comes from | Used for |
|---|---|---|
| `name`, `age` | the character record | every prompt |
| `traits` | the character's `occupation` + `quirk` | every prompt ("Personality: ...") |
| `currently` | the character's `bio` | how the day starts; the daily plan |
| `location` | the character's `place_name` | co-presence, and every prompt ("Right now, X is at ...") |
| `memory` | `MemoryStream`, rehydrated from past runs | everything the agent "knows" |
| `plan`, `substeps`, `current_action` | planning | what the agent is doing this tick |
| `chatting_with` | the world loop | locks an agent out of acting while in conversation |

`identity_summary()` renders the first four into a paragraph that opens
every LLM call an agent makes.

## One tick

`World.step()` (`world.py`) advances the simulation by one tick, which is
30 simulated minutes (`config.TICK_MINUTES`), starting from 6:00 AM.

```
World.step()
  │
  ├─ 1. ACT          one thread per free agent (in parallel)
  │     planning.next_action()
  │       ├─ out of plan items?   generate_daily_plan()     5-8 broad steps for today
  │       ├─ out of substeps?     decompose(next broad step) 3 finer actions,
  │       │                                                  + WHERE: move somewhere?
  │       └─ current_action = next substep
  │     memory.add("X is <action>")
  │
  ├─ 2. PERCEIVE + REACT      sequential, once per co-located pair
  │     for each (a, b) at the same location string:
  │       a.react("b is nearby, currently: ...")  ->  REACT: <new action>  |  CONTINUE
  │       if a reacted with a talk-ish action ("talk", "greet", "ask", ...):
  │         _run_conversation(a, b)   up to 6 alternating lines of dialogue,
  │                                   stored as one "chat" memory in both
  │     (each agent gets at most one conversation per tick)
  │
  └─ 3. REFLECT      one thread per agent (in parallel)
        reflection.reflect()   only if enough importance has piled up
```

Acting and reflecting touch only the agent's own state, so they run one
agent per thread: real concurrent "thinking", which is why the UI's log
fills in from several agents at once. Perceive/react stays sequential,
because a trio in one room produces overlapping pairs like (a,b) and (a,c),
and both mutate `a`.

## Memory

Everything an agent observes, plans, says, or concludes becomes a
`MemoryNode` in its `MemoryStream` (`memory.py`):

```
MemoryNode
  kind          observation | plan | chat | reflection
  description   the text itself
  importance    1-10, rated by the LLM when the memory is added
  embedding     from Ollama's nomic-embed-text
  created_tick, last_accessed_tick
  evidence      for a reflection: ids of the memories it was drawn from
```

Adding a memory costs two model calls: one to rate its importance ("1 is
brushing teeth, 10 is a breakup") and one to embed it.

**Retrieval** is how memory gets into a prompt. Given a query (the current
observation, "a conversation with Lou", a reflection question),
`retrieve()` scores every node on three signals, min-max normalizes each,
and sums them with equal weight:

| Signal | How it's computed |
|---|---|
| recency | rank nodes by `last_accessed_tick`, newest first, then `0.99 ** rank` |
| importance | the stored 1-10 rating |
| relevance | cosine similarity between the node's embedding and the query's |

The top k come back, and each gets its `last_accessed_tick` bumped, so a
memory that keeps proving useful stays "fresh." The reference
implementation sorts recency backwards (a known bug); this one
deliberately favors newer memories.

**Memory persists across runs.** When a run finishes, every event is split
per agent and appended to that character's record in `citystate/`
(`store.append_agent_run()`). The next time the same character is in a
run, `MemoryStream.from_persisted()` rebuilds their stream from those
events without any new model calls. Old memories get negative synthetic
ticks so they always sort as older than the new run's, and the running
importance total is restored so the next reflection triggers on schedule.
This is what lets "today" build on what happened last time instead of
replaying the same day.

## Reflection

Reflection (`reflection.py`) turns raw observations into higher-level
beliefs. It fires once the summed importance of observations since the
last reflection reaches 150 (`REFLECTION_IMPORTANCE_THRESHOLD`):

1. From the 30 most recent observations, ask for the 3 most salient
   high-level questions ("focal points").
2. For each question, retrieve the 10 most relevant memories and ask for 3
   insights, each citing the numbered memories it's based on:
   `Lou doesn't trust Marsh (because of 1, 4)`.
3. Store each insight as a `reflection` memory, with `evidence` pointing
   at the cited memory ids.

Reflections are memories like any other, so they get retrieved into later
plans, reactions, and dialogue. That's how a run can end with agents
acting on conclusions nobody scripted.

## Planning

`planning.py` works top-down, one level less than the paper:

- **The daily plan** (`generate_daily_plan`): 5-8 short items for the
  whole day, in order. The prompt first retrieves memories of past days
  and explicitly asks the model to move the story forward rather than
  reuse the same schedule.
- **Decomposition** (`decompose`): when the current broad item runs out,
  the next one is split into 3 actions of a few minutes each. Each tick
  consumes one action, so a broad item lasts 3 ticks.
- **Movement**: the decompose prompt also asks where the agent should be
  for that whole step, from the city's active places, or `STAY`. The reply
  is matched against the real place list and ignored if it doesn't match,
  so the model can never put an agent somewhere that doesn't exist. Moves
  are instant; there's no pathfinding or travel time.

The paper decomposes recursively, down to 5-15 minute chunks. To add that,
call `decompose()` again on each substep before `next_action()` hands it
out, and keep a cursor per level.

## Meeting and talking

Two agents meet when their `location` strings are equal. Nothing else
brings them together: at the start of a normal run each agent is at their
own grounding place, so two agents only meet if history put them at the
same place or one of their plans moves them there.

When they meet, the first one gets `react()`: its memories relevant to the
other person, its current action, and the choice between `REACT: <new
action>` or `CONTINUE`. A reaction containing a talk-ish word starts a
conversation of up to 6 lines, each generated by `converse_turn()` from
the speaker's memories of the listener and the conversation so far. The
whole transcript is then stored as one `chat` memory in both agents.

## Run options

These arrive from the Simulation node through `routes.py` and
`simulation.run()`:

| Option | Effect |
|---|---|
| `agent_names` | which residents take part (the agents wired into the node) |
| `ticks` | how many 30-minute ticks to run |
| `convene_at` | a place name (from a Location wired into the node): every agent starts there, and they're *anchored* for the whole run, meaning decompose is never offered anywhere else to go. Without anchoring, each agent's own WHERE answer walks them back to their usual haunt within a couple of ticks. |
| `directive` | free text ("they're planning a heist, keep it tense") spliced into every plan, decompose, react, and dialogue prompt via `textutil.directive_block()`. It's a scene nudge for this run only, not a permanent trait. |
| `provider`, `chat_model` | `ollama` (default) or `claude`, and which model |
| `verbose` | colored per-agent tracing in the server terminal (`display.py`) |

`POST /api/agents/stop` sets a flag the loop checks between ticks.

## Keeping the model on the rails

Most of `textutil.py` exists because models drift in predictable ways:

- **Invented characters.** Asked to describe what an agent does next, a
  model happily introduces "Vinnie the bartender." That name then gets
  stored in memory, retrieved later, and turns up in dialogue as if Vinnie
  were real. `cast_constraint()` adds a line to every generating prompt
  listing the only named people who exist and telling the model to refer
  to anyone else generically.
- **Wrong addressee.** Memories retrieved for a conversation can mention
  other people, and a model will sometimes address the listener by one of
  those names. `converse_turn()` states who is in front of the speaker and
  forbids any other name.
- **Chatty replies.** `parse_list_lines()` strips bullets, numbering, and
  "Here are the actions:" preambles; `first_spoken_line()` drops trailing
  commentary like "This line feels like a natural continuation...";
  `extract_tagged_line()` pulls the `WHERE:` line out before the substeps
  are parsed.

## Events, live and persisted

Every step writes a structured event to `recorder.py`: `plan`,
`decompose`, `action`, `move`, `observe`, `react`, `continue`, `dialogue`,
`memory`, `focal`, `insight`, `reflect_pause`. The field shapes are listed
in `recorder.py`'s docstring. The frontend polls `GET /api/agents/events`
and `GET /api/agents/state` while a run is going; the Simulation node's log
is built from those, and its verbose checkbox just filters which kinds it
shows. When the run ends, `recorder.to_dict()` goes to
`citystate.store.append_agent_run()`, which is where memory rehydration
reads from next time.

## Treatments

`treatment.py` is not an agent. It's a single LLM call over a finished run:

1. `build_transcript()` rebuilds the run's full narrative. Each agent's own
   file holds only their half of a conversation, so it collects every
   character's run with the same `started_at` and merges the events back
   into one timeline.
2. `generate_treatment()` asks for a film-noir video vignette: cast,
   synopsis, and a numbered STORYBOARD. Two context blocks keep it
   grounded: `CAST:` carries each participant's real bio (which includes
   appearance and wardrobe), and `SETTING:` carries each location's real
   `architecture` description, so the model stops inventing scenery from
   place names.
3. `parse_storyboard_shots()` splits the storyboard into one line per
   shot. Each shot is required to carry its own `Character:` description,
   because each line becomes a Frame node's standalone image prompt.

It uses its own larger context window (`TREATMENT_CONTEXT_TOKENS`), since
a whole transcript is much longer than a per-tick prompt.

## LLM providers

Every file calls `llm.complete()` or `llm.embed()` and never knows which
backend answers. `llm.py` dispatches to `providers/`:

- **`ollama.py`** is the default: a local Ollama server. Chat model and
  context window are picked by `config.py` from the machine's available
  memory (`hardware.py`), from `llama3.1:8b` on a laptop up to
  `gpt-oss:120b` on an 80 GB GPU. Thinking mode is disabled, because a
  thinking model spends tens of seconds reasoning about every importance
  rating.
- **`claude.py`** calls the Claude Messages API over plain REST, no SDK.
  Needs `ANTHROPIC_API_KEY`.

Embeddings always go to Ollama, whichever chat provider is active, because
Claude has no embeddings endpoint. So a Claude run still needs Ollama
running with `nomic-embed-text` pulled; `llm.check_connection()` verifies
both before the run starts rather than failing on the first memory.

A run makes a lot of calls: each memory added costs an importance rating
and an embedding, and every action, observation, and line of dialogue adds
a memory. Expect small local models to take a while per tick.

## Deliberate simplifications

- No map: a location is a name, and moving is instant.
- One level of plan decomposition instead of recursive.
- A conversation starts only when a reaction's text contains a talk-ish
  word, and runs a fixed 6 lines rather than ending on its own.
- One conversation per agent per tick.
- If no city exists at all, `simulation.py` falls back to a hardcoded
  five-person noir cast at a bar (`AGENT_ROSTER`). Those agents have no
  persisted records, so they start with empty memory every run.
