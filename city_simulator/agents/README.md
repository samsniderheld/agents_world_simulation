# The agent simulation

A minimal implementation of the "Generative Agents" architecture from
[Park et al., 2023](https://arxiv.org/abs/2304.03442): characters that
remember what happens to them, periodically reflect on it, plan their day,
react to whoever they run into, and talk to each other. Hyperparameters
(recency decay, retrieval weights, reflection threshold) are taken directly
from the paper's [reference implementation](https://github.com/joonspk-research/generative_agents),
so behavior tracks the paper as closely as a small rewrite reasonably can.

The cast is a city's residents, generated by `history/` and grounded in its
real places (see `history/characters.py`). A run is started by a Simulation
node in the UI (`POST /api/agents/run`), runs on a background thread, and
streams every event to the frontend live. Afterward, a Treatment node can
turn that run into a film treatment with a shot list.

## Modes

There are two ways to run the simulation. They share one job slot (only one
run of either mode at a time), the same characters, and the same persisted
memories.

| | SCENE | CITY |
|---|---|---|
| Node | Simulation | City Simulation |
| Cast | a few hand-picked residents | up to ~200 **heroes** (the wired-in residents, or all of them) plus up to 1000 **background** residents |
| Cognition | every agent: memory stream, reflection, decomposed planning, dialogue | heroes: the same; background: a daily schedule, a small ring-buffer memory, the LLM only for schedules and lines spoken to heroes |
| Inference | `llm.py`, sync calls from threads | `gateway.py`, batched async calls, one wave at a time |
| Code | the rest of this package | `city/` and `gateway.py` |
| Run request | `POST /api/agents/run` (mode `"scene"`, the default) | the same endpoint with `mode: "city"` |

A persisted run's `meta.mode` says which it was; a run from before modes
existed has none and is treated as SCENE. Everything from "An agent" to
"Treatments" below describes SCENE mode; CITY mode has its own section after
it, and SCENE works exactly as described whether or not CITY is ever used.

## An agent

An `Agent` (`agent.py`) is an identity plus a memory stream:

| Field | Comes from | Used for |
|---|---|---|
| `name`, `age` | the character record | every prompt |
| `traits` | the character's `occupation` + `quirk` | every prompt ("Personality: ...") |
| `currently` | the character's `bio` | how the day starts; the daily plan |
| `location` | the character's `place_name` | co-presence, and every prompt ("Right now, X is at ...") |
| `memory` | `MemoryStream`, rehydrated from past runs | everything the agent "knows" |
| `plan`, `substeps`, `current_action` | planning | what the agent is doing this tick |
| `chatting_with` | the world loop | locks an agent out of acting while in conversation |

`identity_summary()` renders the first four into a paragraph that opens
every LLM call an agent makes.

## One tick

`World.step()` (`world.py`) advances the simulation by one tick. A run
starts at 6:00 AM and a tick is 30 simulated minutes by default
(`config.TICK_MINUTES`); the Simulation node can set both per run. The
planning prompts are told the current time ("It is currently 10:00 PM"),
and decompose asks for substeps that fill exactly one tick ("about 2
hours"), so both settings change what agents do, not just the clock.

```
World.step()
  │
  ├─ 1. ACT          one thread per free agent (in parallel)
  │     planning.next_action()
  │       ├─ first turn?          generate_plan()      the whole run's plan, up to 8
  │       │                                            items spread evenly over its ticks
  │       ├─ entering an item?    decompose(item)      one action per tick it covers,
  │       │                                            + WHERE: move somewhere?
  │       └─ current_action = this tick's action
  │     memory.add("X is <action>")
  │     memory.flush()
  │
  ├─ 2. PERCEIVE + REACT      one thread per location (in parallel)
  │     for each (a, b) at that location, in order:
  │       a.react("b is nearby, currently: ...")  ->  REACT: <new action>  |  CONTINUE
  │       if a reacted with a talk-ish action ("talk", "greet", "ask", ...):
  │         _run_conversation(a, b)   ONE call writes up to 6 alternating lines,
  │                                   stored as one "chat" memory in both
  │     (each agent gets at most one conversation per tick)
  │     memory.flush() for everyone who met
  │
  └─ 3. REFLECT      one thread per agent (in parallel)
        reflection.reflect()   only if enough importance has piled up
```

Acting and reflecting touch only the agent's own state, so they run one
agent per thread: real concurrent "thinking", which is why the UI's log
fills in from several agents at once. Meetings run one thread per
location: an agent is only ever in one place, so two locations never share
an agent. Inside a location the pairs stay sequential, because a trio in
one room produces overlapping pairs like (a,b) and (a,c), and both mutate
`a`.

The providers cap how many calls are in flight at once
(`config.MAX_CONCURRENCY`), so a tick with many agents queues its calls
instead of flooding a local server.

## Memory

Everything an agent observes, plans, says, or concludes becomes a
`MemoryNode` in its `MemoryStream` (`memory.py`):

```
MemoryNode
  kind          observation | plan | chat | reflection
  description   the text itself
  importance    1-10, rated by the LLM when the memory is added
  embedding     from Ollama's nomic-embed-text
  created_tick, last_accessed_tick
  evidence      for a reflection: ids of the memories it was drawn from
```

A new memory is queued, not scored straight away. `flush()`, called at
the end of each phase of a tick, scores everything queued for that agent
in two calls: one prompt that rates all of their importances at once ("1
is brushing teeth, 10 is a breakup"), and one batched embedding request.
Until the flush, a queued memory counts as importance 5 and isn't
retrievable, which never matters because every phase flushes before the
next one reads.

**Retrieval** is how memory gets into a prompt. Given a query (the current
observation, "a conversation with Lou", a reflection question),
`retrieve()` scores every node on three signals, min-max normalizes each,
and sums them with equal weight:

| Signal | How it's computed |
|---|---|
| recency | rank nodes by `last_accessed_tick`, newest first, then `0.99 ** rank` |
| importance | the stored 1-10 rating |
| relevance | cosine similarity between the node's embedding and the query's |

The top k come back, and each gets its `last_accessed_tick` bumped, so a
memory that keeps proving useful stays "fresh." The reference
implementation sorts recency backwards (a known bug); this one
deliberately favors newer memories.

**Memory persists across runs.** When a run finishes, every event is split
per agent and appended to that character's record in `citystate/`
(`store.append_agent_run()`). The next time the same character is in a
run, `MemoryStream.from_persisted()` rebuilds their stream from those
events without any new model calls. Old memories get negative synthetic
ticks so they always sort as older than the new run's, and the running
importance total is restored so the next reflection triggers on schedule.
This is what lets "today" build on what happened last time instead of
replaying the same day.

## Reflection

Reflection (`reflection.py`) turns raw observations into higher-level
beliefs. It fires once the summed importance of observations since the
last reflection reaches 150 (`REFLECTION_IMPORTANCE_THRESHOLD`):

1. From the 30 most recent observations, ask for the 3 most salient
   high-level questions ("focal points").
2. For each question, retrieve the 10 most relevant memories and ask for 3
   insights, each citing the numbered memories it's based on:
   `Lou doesn't trust Marsh (because of 1, 4)`.
3. Store each insight as a `reflection` memory, with `evidence` pointing
   at the cited memory ids.

Reflections are memories like any other, so they get retrieved into later
plans, reactions, and dialogue. That's how a run can end with agents
acting on conclusions nobody scripted.

## Planning

`planning.py` works top-down, one level less than the paper:

- **The plan** (`generate_plan`): on an agent's first turn it plans the
  whole run, sized to it: "the next 7 days, from Day 1, 06:00 AM until
  Day 8, 06:00 AM" for a week of day-long ticks, "the next 4 hours" for
  8 half-hour ticks. It asks for one item per tick, up to 8
  (`MAX_PLAN_ITEMS`); a longer run gets 8 broader items. The prompt first
  retrieves memories of past runs and asks the model to move the story
  forward rather than repeat them.
- **Pinned to ticks**: the items are spread evenly over the run's ticks,
  and each item is split into exactly as many actions as it has ticks (a
  one-tick item becomes one action covering the whole tick). An agent who
  spends a tick in conversation resumes wherever the clock says, so the
  rest of the plan never slides later.
- **Movement**: the decompose prompt also asks where the agent should be
  for that whole step, from the city's active places, or `STAY`. The reply
  is matched against the real place list and ignored if it doesn't match,
  so the model can never put an agent somewhere that doesn't exist. Moves
  are instant; there's no pathfinding or travel time.

The paper decomposes recursively, down to 5-15 minute chunks. To add that,
call `decompose()` again on each substep before `next_action()` hands it
out, and keep a cursor per level.

## Meeting and talking

Two agents meet when their `location` strings are equal. Nothing else
brings them together: at the start of a normal run each agent is at their
own grounding place, so two agents only meet if history put them at the
same place or one of their plans moves them there.

When they meet, the first one gets `react()`: its memories relevant to the
other person, its current action, and the choice between `REACT: <new
action>` or `CONTINUE`. A reaction containing a talk-ish word starts a
conversation. One prompt carries both identities, each one's memories of
the other and the directive, and asks for the whole exchange at once, up
to 6 lines of `Name: line`. `_parse_conversation()` matches each line to a
speaker by name, falls back to alternating, and strips stage directions.
The transcript is stored as one `chat` memory in both agents. Writing the
scene in one call makes it cheaper and more coherent than six separate
turns, since the model can see where the exchange is going.

## Run options

These arrive from the Simulation node through `routes.py` and
`simulation.run()`:

| Option | Effect |
|---|---|
| `agent_names` | which residents take part (the agents wired into the node) |
| `ticks`, `tick_minutes`, `start_time` | how many ticks to run, how many simulated minutes each lasts, and the time of day it starts (the last two are stored with the run so a treatment rebuilds the right timestamps) |
| `convene_at` | a place name (from a Location wired into the node): every agent starts there, and they're *anchored* for the whole run, meaning decompose is never offered anywhere else to go. Without anchoring, each agent's own WHERE answer walks them back to their usual haunt within a couple of ticks. |
| `directive` | free text ("they're planning a heist, keep it tense") spliced into every plan, decompose, react, and dialogue prompt via `textutil.directive_block()`. It's a scene nudge for this run only, not a permanent trait. |
| `provider`, `chat_model` | `ollama` (default), `claude`, or `openai` (any OpenAI-compatible server), and which model |
| `verbose` | colored per-agent tracing in the server terminal (`display.py`) |

`POST /api/agents/stop` sets a flag the loop checks between ticks.

## Keeping the model on the rails

Most of `textutil.py` exists because models drift in predictable ways:

- **Invented characters.** Asked to describe what an agent does next, a
  model happily introduces "Vinnie the bartender." That name then gets
  stored in memory, retrieved later, and turns up in dialogue as if Vinnie
  were real. `cast_constraint()` adds a line to every generating prompt
  listing the only named people who exist and telling the model to refer
  to anyone else generically.
- **Wrong addressee.** Memories retrieved for a conversation can mention
  other people, and a model will sometimes address the listener by one of
  those names. The conversation prompt states exactly who is present and
  forbids any other name.
- **Chatty replies.** `parse_list_lines()` strips bullets, numbering, and
  "Here are the actions:" preambles; `_parse_conversation()` drops
  commentary lines that aren't `Name: line`; `extract_tagged_line()` pulls the `WHERE:` line out before the substeps
  are parsed.

## Events, live and persisted

Every step writes a structured event to `recorder.py`: `plan`,
`decompose`, `action`, `move`, `observe`, `react`, `continue`, `dialogue`,
`memory`, `focal`, `insight`, `reflect_pause`. The field shapes are listed
in `recorder.py`'s docstring. The frontend polls `GET /api/agents/events`
and `GET /api/agents/state` while a run is going; the Simulation node's log
is built from those, and its verbose checkbox just filters which kinds it
shows. When the run ends, `recorder.to_dict()` goes to
`citystate.store.append_agent_run()`, which is where memory rehydration
reads from next time.

## Treatments

`treatment.py` is not an agent. It's a single LLM call over a finished run:

1. `build_transcript()` rebuilds the run's full narrative. Each agent's own
   file holds only their half of a conversation, so it collects every
   character's run with the same `started_at` and merges the events back
   into one timeline.
2. `generate_treatment()` asks for a film-noir video vignette: cast,
   synopsis, and a numbered STORYBOARD. Two context blocks keep it
   grounded: `CAST:` carries each participant's real bio (which includes
   appearance and wardrobe), and `SETTING:` carries each location's real
   `architecture` description, so the model stops inventing scenery from
   place names.
3. `parse_storyboard_shots()` splits the storyboard into one line per
   shot. Each shot is required to carry its own `Character:` description,
   because each line becomes a Frame node's standalone image prompt.

It uses its own larger context window (`TREATMENT_CONTEXT_TOKENS`), since
a whole transcript is much longer than a per-tick prompt.

## LLM providers

Every file calls `llm.complete()` or `llm.embed()` and never knows which
backend answers. `llm.py` dispatches to `providers/`:

- **`ollama.py`** is the default: a local Ollama server. Chat model and
  context window are picked by `config.py` from the machine's available
  memory (`hardware.py`), from `llama3.1:8b` on a laptop up to
  `gpt-oss:120b` on an 80 GB GPU. Thinking mode is disabled, because a
  thinking model spends tens of seconds reasoning about every importance
  rating.
- **`claude.py`** calls the Claude Messages API over plain REST, no SDK.
  Needs `ANTHROPIC_API_KEY`.
- **`openai_compat.py`** talks to any server with an OpenAI-style
  `/v1/chat/completions` endpoint. That covers `mlx_lm.server` on Apple
  Silicon, vLLM and SGLang on a GPU box, and LM Studio. These servers batch
  many requests on the GPU at once, so they get far more out of the
  parallel tick than Ollama does. It retries 429 and 5xx replies and strips
  `<think>` blocks from reasoning models.

| Setting | Default | |
|---|---|---|
| `OPENAI_COMPAT_BASE_URL` | `http://localhost:8080/v1` | mlx_lm.server's default port; vLLM uses 8000, SGLang 30000 |
| `OPENAI_COMPAT_MODEL` | first model the server lists | |
| `OPENAI_COMPAT_API_KEY` | empty | only if the server wants one |

`config.MAX_CONCURRENCY` sets how many chat calls each provider may have
in flight: 4 for Ollama, 8 for Claude, 16 for OpenAI-compatible servers.
`EMBED_MAX_CONCURRENCY` does the same for embeddings.

Embeddings always go to Ollama, whichever chat provider is active, because
Claude has no embeddings endpoint. So a Claude or OpenAI-compatible run
still needs Ollama running with `nomic-embed-text` pulled;
`llm.check_connection()` verifies both before the run starts rather than
failing on the first memory.

A run still makes a lot of calls: every action, observation, and
conversation adds memories, and each agent's queued memories cost two
calls per phase. Expect small local models to take a while per tick.

## CITY mode

A mass simulation: heroes with full cognition, and a crowd of background
residents who make the city feel inhabited without costing an LLM call
each per tick. It runs at reduced scale on the default local Ollama on a Mac
and at full scale against a GPU server (vLLM, SGLang, llama.cpp, MLX).

### Tiers

**Heroes** are saved characters -- the ones wired into the City Simulation
node, or every generated resident if none are. `CityHero` is a SCENE
`Agent`: same identity paragraph, plan fields and `MemoryStream` semantics
(`CityMemoryStream` keeps the scoring formula and persisted shape, but its
memories are scored in the tick's batched memory wave, and relevance is
vectorised with numpy when it's installed). A CITY run appends each hero's
events to their record exactly as SCENE does, so either mode remembers the
other's runs (the node's "persist hero memories" toggle, on by default).

**Background residents** come from `city/population.py`: names from
`history/data/names.yaml`, jobs that fit the city's active places (a
bartender works at a bar, a longshoreman at the docks), a haunt, a home, a
day or night shift, and a one-line bio from `history/grammar.py`. No LLM
calls, and deterministic from the seed; they're saved once per city in
`citystate/data/cities/<id>/background.json` and reused. Each gets one JSON
schedule per sim-day from the model (`[{start, end, activity, place}]`,
validated against the active places; up to the profile's
`llm_schedule_cap`, residents near the heroes first) or an occupation
template, and follows it with no further calls. Their memory is a ring
buffer of 40 entries with heuristic importance, retrieved by recency plus
name/keyword overlap.

**Promotion**: a background resident who has dealt with heroes 3 times, or
one picked from the node's list, becomes a hero at the end of the tick. Their
ring buffer becomes `MemoryNode`s (one embedding batch), and they plan from
the next tick.

### One CITY tick

Each wave gathers every request it needs, sends them in one batch, and
applies the results; all state changes happen between waves on one event
loop, so nothing needs a lock.

```
CityWorld.step()                                            (city/world.py)
  │
  ├─ PLAN        heroes without a plan -> plan for the rest of the run
  │              background, first tick of each sim-day -> one JSON schedule
  ├─ DECOMPOSE   heroes entering a plan item -> {actions, where} (JSON)
  │              background -> the schedule block for this time of day
  ├─ ENCOUNTERS  group everyone by place; per place up to 3 pairs, nobody
  │              in two (hero-hero, then hero-background, then background)
  │              background-background: settled in Python, no LLM
  ├─ REACT       one call per hero encounter -> TALK / REACT / CONTINUE
  ├─ DIALOGUE    every conversation advances one line per batch, in
  │              lockstep, up to 6 lines or [END]; background speakers
  │              use the background model
  ├─ MEMORY      every hero memory from this tick: one importance call per
  │              hero + one embed_many for all of them
  ├─ REFLECT     heroes over the threshold: focal-point wave, insight wave
  └─ PROMOTE     background residents who've earned it (or were picked)
```

Every hero call's prompt names only the people relevant to it (who's
there, who they're talking to, who they know best) and keeps SCENE's rule
against inventing named people. The directive applies to heroes, and to a
background resident only when it names them, their job, or everyone.

### Inference: `gateway.py`

One asyncio loop per run, one `httpx.AsyncClient`. `generate_many()` and
`embed_many()` send a wave's requests concurrently, capped per server by an
AIMD limiter (a 429/503/timeout halves the allowance, successes grow it back),
with retries, backoff and jitter; a request that still fails comes back as a
typed failure for that agent only. Structured calls send a JSON schema
natively where the server supports it (Ollama `format`, vLLM/SGLang
`response_format`, llama.cpp `json_schema`), otherwise in the prompt, with
one repair attempt. Prompts are four parts -- shared city prefix, tier
instructions, identity, the call itself -- and batches are submitted sorted
by prefix so prefix-caching servers reuse their KV cache.

### Hardware profiles

`hardware.py`'s `CITY_PROFILES` (the node's hardware picker; "auto"
detects):

| Profile | Backend | Hero / background model | In flight | Agents | Hero cap | LLM schedules/day |
|---|---|---|---|---|---|---|
| `mac` | Ollama | `llama3.1:8b` / `llama3.2:3b` | 4 (8 with 48 GB+) | 200 | 30 | 40 |
| `rtx5090` | vLLM | `Qwen/Qwen3-30B-A3B-Instruct-2507` / `Qwen/Qwen3-4B-Instruct-2507` | 128 | 1000 | 200 | 1000 |
| `h100` | vLLM | `openai/gpt-oss-120b` / `Qwen/Qwen3-8B` | 256 | 2000 | 200 | 2000 |

The node can override each tier's provider and model. A tier whose model
isn't available falls back to the hero model (on the Mac: pull
`llama3.2:3b` for a faster background tier). For vLLM, `CITY_HERO_BASE_URL`
and `CITY_BACKGROUND_BASE_URL` point the tiers at their servers (default:
`OPENAI_COMPAT_BASE_URL`). `./start_ollama.sh` starts Ollama with
`OLLAMA_NUM_PARALLEL` from the profile and `OLLAMA_MAX_LOADED_MODELS=2`, so
both tiers stay loaded. Embeddings always come from Ollama's
`nomic-embed-text`.

### Zooming in: CITY -> SCENE

1. Run a City Simulation, then pause or stop it (or come back to a finished
   one -- its summary is saved in `citystate/data/cities/<id>/city_runs/`).
2. Open *zoom into a scene* on the node, pick a place and a window of ticks,
   and click *create scene*.
3. `city/zoom.py` finds who was at that place in that window (heroes first,
   up to 8). Background residents among them are promoted to saved
   characters: a cheap LLM call writes a proper dossier (appearance and
   wardrobe included), and their last CITY memories go into their new
   record so SCENE's memory stream starts with something.
4. The canvas gets a Simulation node, with those residents' Agent nodes and
   the Location wired in, set to the window's start time and length and the
   CITY run's directive. Run it for full cognition on that moment.

### Treatments of CITY runs

A Treatment wired to a City Simulation node builds its transcript from the
heroes only (their actions and dialogue, plus lines background residents
said to them), optionally narrowed on the node to one place and a range of
ticks, and capped in length. SCENE runs are treated exactly as before.

### Watching a run

The live log is a ring buffer with level of detail: heroes get every event;
background residents get moves, encounters and promotions, plus one
`tick_summary` per tick (occupancy by place). `GET /api/agents/events`
pages with a `seq` cursor and filters (`tier=hero|background|all`, `kinds`,
`agent`, `place`, `limit`); for SCENE runs it answers exactly as before.
Every tick ends with a `metrics` event -- wall time per wave, requests,
tokens, retries, failures, tok/s, calls per agent per tier -- which the node
shows. `POST /api/agents/city/pause`, `/resume`, `/promote` control a
running CITY run.

### Asking what's going on

The City node's *what's going on in the city* panel has two tools, both
answered by the run's hero model from what the run recorded
(`city/insight.py`; `POST /api/agents/city/report`, `/city/ask`):

- **City report**: a briefing -- the main storylines and who's in them, the
  places with crowds and tension, the residents to watch. Asking again
  passes the previous briefing, so the new one also says what changed.
- **Ask the city**: a free-form question ("who knows about the payroll?"),
  answered from the log lines that share the most names and words with it,
  plus the latest ones, naming who said or did what, when and where.

Both read the live run while it's in memory (running, paused or finished),
or the latest saved run after a restart, cut to fit the model's context.

### Benchmark and tests

```bash
python3 -m agents.city.bench                  # 50/200/500/1000 agents on the stub server
python3 -m agents.city.bench --real --profile mac --agents 50 --ticks 2
python3 -m unittest discover -s tests -t .    # includes the SCENE regression snapshot
```

On the stub server (0.05 s per request, 64 in flight, 16 ticks of 90
minutes), background residents average 0.08-0.12 LLM calls per tick, and a
tick's time tracks the ideal number of round trips: 0.6 s at 50 agents, 0.9 s
at 1000. `tests/test_scene_regression.py` snapshots a five-agent SCENE run
(event sequence and every prompt) against a deterministic stub; it has
passed unchanged through every CITY change.

## Deliberate simplifications

- No map: a location is a name, and moving is instant.
- One level of plan decomposition instead of recursive.
- A conversation starts only when a reaction's text contains a talk-ish
  word, and is written in one call: up to 6 lines, ending early if it
  reaches a natural close.
- One conversation per agent per tick.
- If no city exists at all, `simulation.py` falls back to a hardcoded
  five-person noir cast at a bar (`AGENT_ROSTER`). Those agents have no
  persisted records, so they start with empty memory every run.
